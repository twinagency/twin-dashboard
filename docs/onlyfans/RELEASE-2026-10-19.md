## Image and deployment owners

The native image was built in AWS CodeBuild project `twin-onlyfans-release`,
outside the live customer server, from an encrypted private S3 ZIP of the exact
Git commit. Build `cfe1f052-48c4-405c-94e4-4ba7d9b3f22d` succeeded.
The image is
`323149985112.dkr.ecr.ap-southeast-2.amazonaws.com/twin-onlyfans@sha256:3394bdb73c777e034b883bdbae680c84712ee1b138b4b45d0f9b4cafe856348f`.
Its OCI revision label names the source commit. The build role can read that
one source object and push the dedicated ECR repository and its own logs; it
does not administer customer runtimes or databases.

The existing dashboard workflow builds and deploys the integrated dashboard by
digest. Its container joins `twin-onlyfans_default` so the server-only backend
origin resolves privately. The existing production host is reached using SSM;
a Desktop Commander agent on that server is not necessary.

## Native service layout

The source lives under `/opt/twin-onlyfans/releases/<source-commit>`.
Private configuration lives under `/etc/twin-onlyfans/`, outside source control.
The base compose file remains the source owner; a host override pins the image
digest, logging and resource limits.

- PostgreSQL, API and worker each have a 256 MiB memory ceiling and 0.5 CPU.
  These are initial deployment bounds, not evidence of 200-creator capacity.
- PostgreSQL publishes only loopback `127.0.0.1:5438`; the API publishes only
  loopback `127.0.0.1:8788` and is also reachable on the private compose network.
- The worker uses the host network to read the existing Twin admin API on real
  loopback `http://127.0.0.1:3001`, retaining both its bearer and network gate.
  It uses the private loopback PostgreSQL port. No forwarded IP is fabricated.
- The worker reuses the existing private admin API key when configured. No
  Supabase service credential is copied into the native runtime.
- The named PostgreSQL and image volumes retain existing database/media owners.
  API preview storage is read-only; worker preview storage is writable.

The new database is initialized only when its public schema is empty. Startup
does not migrate an existing database. A schema check precedes API/worker
startup. The private encryption key must be retained separately from database
dumps; never delete these volumes as a rollback.

Account registration leaves sending disabled. There is no selected real
OnlyFans account or captured session in this release. Ledger intake remains
off pending provider validation. Requested vault still previews and inherited
Twin facts are configured; availability still depends on an authorized bound
creator and current provider evidence.
