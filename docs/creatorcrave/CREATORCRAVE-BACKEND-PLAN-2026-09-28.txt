DATA MODEL (new Supabase project)
- creators: handle, display name, profile pic, bio, ton_wallet_address,
  stars_link (optional fallback), status (pending/approved/rejected), created_at
- content: creator_id, type (photo/video), storage_path, price_nanoton (0 for
  free), caption, created_at
- orders: content_id, buyer_wallet_address, amount_nanoton, memo (order id we
  generate), status (pending/confirmed/delivered), tx_hash (filled once
  matched), created_at
- No payments table holding OUR money — we never custody funds. orders is a
  record of what we've confirmed on-chain, not a ledger of funds we hold.

TELEGRAM SIDE
- New bot via BotFather, separate from all Twin bots.
- Mini app registered against that bot.
- 3 pages: Explore (scroll feed, mixed creators/types/free-paid), Trending
  (leaderboard by sales/activity), Account (fan's purchases + own uploads if
  also a creator — one account type, not two apps).

CREATOR FLOW
1. Sign up: handle, pic, bio, TON wallet address (Stars link optional fallback)
2. Goes into a moderation queue — pending until approved
3. Once approved: upload content (photo/video), set price in TON, mark free
   or paid
4. Appears in Explore/Trending once live

FAN FLOW
1. Browse Explore/Trending, no login needed for browsing
2. To buy: connect TON wallet (TON Connect, Telegram's native wallet picker)
3. Tap buy -> we generate an order (memo/order id) -> TON Connect sends
   payment to the creator's wallet with that memo attached as a comment
4. Wait for confirmation (see below) -> content unlocks in Account tab

PAYMENT CONFIRMATION — THE PIECE THAT NEEDS REAL ENGINEERING
Verified against TON's own docs (not assumed):
- TON Connect's sendTransaction call resolving does NOT mean the payment
  landed. It resolves once the wallet signs and broadcasts, before finality.
  TON's own guidelines say explicitly: "You should never use external
  message tracking for payment processing purposes."
- Correct approach: every transaction carries a comment/memo (the order id)
  via the payload field. A backend service polls each creator's wallet
  address through a TON API (TonAPI or toncenter), watching for new incoming
  transactions, matching by memo + amount. Only when a match is confirmed
  on-chain do we mark the order "confirmed" and unlock content.
- Typical finality is about 1 second per transaction; poll with a few
  seconds of margin to be safe.
- This poller/matcher is new code, not something TON Connect gives for free.
  It's the one place a bug directly costs money (deliver before confirmed =
  give away content for nothing).

MODERATION
- Pending queue, human approval before a creator goes live. Not automatable
  day one — someone (you, or whoever you assign) reviews each signup.
- Same policy for every creator, Twin's own (Alanna etc.) included — no
  special fast lane, for fairness and to build the habit of reviewing before
  content goes live.

HIGH LEVEL

CreatorCrave is a new, separate product: a 3-page Telegram mini app (Explore,
Trending, Account) where anyone signs up, lists content, and gets paid
directly to their own TON wallet. We host the listing and confirm payment;
we never touch money. Infra and data stay fully separate from Twin's boxes
and Supabase project, since this is a different brand with different
liability (open signup, third-party content, no vetting like Twin's own 18
clones get).

The one place this needs real engineering, not just wiring up an SDK: TON
Connect's payment confirmation is broadcast-only, not proof of finality. A
backend poller has to independently verify each payment against the chain
before content unlocks. Everything else, the pages, the signup form, the
upload flow, is straightforward and reuses patterns already built for Twin's
existing mini app.

Nothing has been provisioned yet. AWS security group creation was attempted
and blocked by the sandbox's security classifier (opening inbound ports is
correctly treated as a change that needs your explicit sign-off) — this plan
sits ready for your go-ahead on infra, not built out yet.
